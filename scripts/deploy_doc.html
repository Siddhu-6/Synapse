The one thing to know first By default Synapse runs entirely on your machine with a local model (Ollama). That is private and free, but a local 7B model takes roughly 30–70 seconds to plan a task. A free Groq key (section 6) brings that to 2–5 seconds and plans better, with the local model kept as an automatic fallback. If you do one optional thing, do that one.

Conventions in this guide

  • Commands are for the macOS Terminal (zsh). Paste one line at a time; lines starting with # are comments.
  • ~/Desktop/synapse is the project folder. Replace it if yours is elsewhere.
  • Anything in <angle brackets> is a placeholder you must replace, brackets included.

Hardware

16 GB RAM (your MacBook Air M4) runs a 7B model comfortably; 8 GB works but swaps. Apple Silicon uses the GPU automatically. Disk: about 6 GB for models, plus your vault.

Never run Ollama on a cloud VM Cloud CPUs manage a few tokens per second, which makes the assistant unusable. Anywhere other than your own Mac, use a hosted model (sections 3 and 6).

2Run it with uv

First run takes about 10 minutes, mostly downloads. After that it is two commands.

2.1  Start the model server

Terminal 1 — leave it running (or run brew services start ollama once and it starts at login):

ollama serve

Terminal 2 — download the models:

ollama pull qwen2.5:7b-instruct   # planner/writer, ~4.7 GB
ollama pull nomic-embed-text      # memory search, ~270 MB, optional

2.2  Install the project

cd ~/Desktop/synapse
uv sync --extra dev --extra google

uv sync downloads Python 3.12 if needed, creates .venv/, and installs exactly the versions pinned in uv.lock. The extras: dev = tests, google = Gmail and Calendar, crew = the CrewAI research crew (large; add --extra crew if you want it).

2.3  Create your settings file

cp .env.example .env
open -e .env

At minimum set SYNAPSE_VAULT_PATH to the absolute path of your Obsidian vault (e.g. /Users/<you>/Documents/MyVault). Section 3 explains every other line.

2.4  Build the dashboard

cd web
npm install
npm run build
cd ..

Repeat only when you change something under web/src. For UI work, npm run dev in web/ serves on port 5173 with hot reload.

2.5  Check and start

uv run synapse doctor
uv run synapse-api

Open http://127.0.0.1:8000. doctor checks Ollama, the model, every MCP server, Google, and prints the vault path it will really use — compare it with Obsidian.

Daily use cd ~/Desktop/synapse then uv run synapse-api (with Ollama running). That is all. uv run always uses the project's own environment — no source .venv/bin/activate needed. Section 10.1 makes even this automatic.

2.6  Useful uv commands

3.3  Paths

VariableDefaultMeaning · production advice

3.4  Budgets and guard rails

VariableDefaultMeaning · production advice
SYNAPSE_TOOL_TIMEOUT30Seconds before a tool call is abandoned (read-only tools are retried once). 45 if research often times out.
SYNAPSE_MAX_STEPS6Longest plan. 6–8 is right; longer plans are slower and more fragile, not smarter.
SYNAPSE_MAX_REPLANS1Re-plans after a failed step. Keep 1: a second replan rarely succeeds where the first failed.
SYNAPSE_MAX_LLM_CALLS20Hard per-run budget; the loop guard. With a paid provider this is also your cost ceiling per request.
SYNAPSE_PARALLEL_STEPS2Independent read-only steps run together. 3 on a hosted model; keep 2 on local Ollama.
SYNAPSE_CREW_TIMEOUT420Seconds for a CrewAI research report. 600 local, 300 hosted.

3.6  API and security

VariableDefaultMeaning · production advice
SYNAPSE_HOST127.0.0.1Keep 127.0.0.1. Reach it from outside through a tunnel or reverse proxy, never by binding 0.0.0.0 on a public machine. (Docker sets 0.0.0.0 inside the container but publishes only to 127.0.0.1.)
SYNAPSE_PORT8000Change only if 8000 is taken.
SYNAPSE_API_TOKENunsetRequired before exposure. Without it every route is open — including the ones that send email. The dashboard asks for it once and keeps it in the browser.

3.7  Integrations

VariableDefaultMeaning · production advice
SYNAPSE_NOTION_TOKENunsetEnables the Notion tools (section 8).
SYNAPSE_N8N_WEBHOOKSunsetname=url pairs, comma-separated, no spaces. An allowlist: Synapse can call only these. Use production URLs (/webhook/, not /webhook-test/) over https.

Secrets .env and data/ (which holds google_token.json) are git-ignored — keep it that way. On a server, set them as environment variables or a root-only .env (chmod 600 .env). If a key ever lands in a commit, rotate it at the provider; deleting the file is not enough.

5Put it on GitHub

Your portfolio copy. CI runs the tests and evals on every push.

5.1  One-time git setup

git config --global user.name "<Your Name>"
git config --global user.email "<the email on your GitHub account>"

5.2  Check nothing secret will be committed

.gitignore already excludes .env, data/, SynapseVault/, .venv/, web/node_modules/ and the built dashboard. Confirm before the first commit:

cd ~/Desktop/synapse
git init -b main
git add .
git status

In the list, .env, data/ and google_credentials.json must not appear. If one does, stop and add it to .gitignore, then git rm --cached <file>.

git commit -m "Synapse: agentic assistant (LangGraph, MCP, CrewAI)"

5.3  Create the repository and push

Option A — GitHub CLI (easiest)

gh auth login                         # choose GitHub.com, HTTPS, log in with browser
gh repo create synapse --public --source=. --push

Option B — website

  1. github.com → New repository → name synapse. Do not tick “Add a README”, .gitignore or licence (they would conflict with your first push).
  2. Copy the HTTPS URL, then:
git remote add origin https://github.com/<your-username>/synapse.git
git push -u origin main

When asked for a password, use a personal access token (GitHub → Settings → Developer settings → Personal access tokens → Fine-grained → repository access: synapse, Contents: read and write), not your account password.

5.4  CI

.github/workflows/ci.yml runs automatically on every push to main and on pull requests: lint, the test suite, the evaluation suite (report uploaded as an artifact), the dashboard build and a Docker build. Watch it under the repository's Actions tab. No secrets are needed — tests script the model.

Add the status badge to the top of README.md:

5.6  Making it portfolio-ready

  • Repository description and topics: langgraph, mcp, crewai, agents, llmops, obsidian
  • A screenshot or short GIF of a run at the top of the README (Journal with “Show working” open, and the Agents view)
  • A LICENSE file (MIT is usual): GitHub → Add file → Create new file → name it LICENSE → choose a template
  • Pin the repository on your profile
  • Search the history once for leaked keys: git log -p | grep -iE "gsk_|ntn_|api_key|secret"
If you ever push a secret Revoke it at the provider immediately (Groq, Notion, Google Cloud), then generate a new one. The old value stays in git history even after you delete the file, and public repositories are scanned by bots within minutes.

6Fast model (Groq)

Free tier, OpenAI-compatible, 10–30× faster than a local 7B model.
  1. Go to console.groq.com → sign in → API Keys → Create API Key. Copy it (starts with gsk_).
  2. In .env: 
    SYNAPSE_FAST_BASE_URL=https://api.groq.com/openai/v1
SYNAPSE_FAST_MODEL=llama-3.3-70b-versatile
SYNAPSE_FAST_API_KEY=<gsk_...>
  3. Restart the API. The sidebar footer changes from local to fast + local.

Free tiers have per-minute and per-day limits. When Groq refuses a call, Synapse falls back to Ollama for that call, so a heavy day gets slower rather than broken. Cerebras (https://api.cerebras.ai/v1, model llama-3.3-70b) works the same way if you want a second option.

Privacy trade-off With a fast provider, your prompts — including note excerpts used for the task — go to that provider. Leave the three lines unset for fully local operation.

7Gmail & Google Calendar

About 15 minutes, once. Sending and event creation always ask for your approval.
  1. console.cloud.google.com → project selector → New project → name it synapse → Create.
  2. APIs & Services → Library: enable Gmail API, then Google Calendar API.
  3. OAuth consent screen (Google Auth Platform → Branding/Audience): User type External; app name Synapse; your email as support and developer contact. Under Audience → Test users add your own Gmail address. Leave the app in Testing.
  4. Credentials → Create credentials → OAuth client ID → Application type Desktop app → Create → Download JSON.
  5. Move it into the project: 
    mv ~/Downloads/client_secret_*.json ~/Desktop/synapse/data/google_credentials.json
  6. Authorise (a browser tab opens; choose your account; on “Google hasn't verified this app” click Continue — it is your own app): 
    uv run python -m synapse.integrations.google_auth
  7. Restart the API. uv run synapse doctor should print Google: connected and the Tools tab lists gmail_send, gmail_search, calendar_create_event…
Testing-mode tokens expire after 7 days If Gmail tools start failing with an auth error, re-run step 6. To stop the weekly expiry you would need to publish the app, which requires Google verification for Gmail scopes — not worth it for personal use.

Emails are sent as plain text plus clean HTML (tables and lists render properly), never with attachments; the content is written into the body before you approve. Bodies containing placeholder text are refused and the run re-plans to fetch real data.

8Notion

Five minutes. Synapse can only see pages you explicitly share with it.
  1. Open notion.so/profile/integrations (older link: notion.so/my-integrations) → New integration.
  2. Name Synapse, pick your workspace, type Internal → Save.
  3. Capabilities: Read content, Update content, Insert content. Copy the Internal Integration Secret (starts with ntn_).
  4. .env: SYNAPSE_NOTION_TOKEN=<ntn_...> and restart.
  5. In Notion, open each page or database Synapse should use → ⋯ (top right) → Connections → Synapse. Sharing a parent page shares everything under it.

Try: “Add a row to my Reading List database: Designing Data-Intensive Applications, status To read”. Anything not shared returns “not found”, and Synapse says so rather than guessing.

9n8n: WhatsApp, Telegram, Slack, Sheets

n8n is the bridge to every service Synapse has no built-in tool for.

9.1  How it fits together

An n8n workflow is a graph of nodes on a canvas, joined left to right. The first node is a trigger; each following node receives the previous node's JSON output. Synapse talks to n8n in two directions:

Synapserun_workflow("telegram", {to, message})
→
WebhookPOST /webhook/<id>
→
Telegram / WhatsApp / Slacksend the message
WhatsApp Triggersomeone messages you
→
HTTP RequestPOST /api/messages
→
Synapsereply, or notify you

Outbound: Synapse calls run_workflow(name, payload). The name must be registered in SYNAPSE_N8N_WEBHOOKS; the payload is always {"to": "…", "message": "…"} (plus "subject" when relevant). Inbound: n8n forwards a received message to Synapse's /api/messages endpoint.

Three n8n facts that trip everyone up

  1. Test URL vs production URL. Every Webhook node has two. The test URL (/webhook-test/…) works only while you have clicked Listen for test event. The production URL (/webhook/…) works only when the workflow is Active (toggle at the top; newer versions call it Publish). Register the production URL.
  2. The POST body is under body. In later nodes the message is {{ $json.body.message }}, not {{ $json.message }}.
  3. n8n must be able to reach Synapse for inbound flows (and vice versa for outbound). n8n Cloud cannot reach localhost on your Mac — use a tunnel (section 10.4).

9.3  Secure every Synapse webhook

  1. Generate a secret: openssl rand -hex 24. Put it in .env as SYNAPSE_N8N_SECRET.
  2. In n8n: Credentials → New → Header Auth. Name: X-Synapse-Secret. Value: the secret. Save as “Synapse secret”.
  3. In every Webhook node below: Authentication → Header Auth → Synapse secret.

Now a request without the header gets 403 from n8n, even if someone learns the URL.

9.4  Recipe: Telegram messages (start here — free and easy)

WebhookPOST · Header Auth
→
TelegramSend Message
  1. In Telegram, message @BotFather → /newbot → name it → copy the bot token.
  2. Send your new bot any message. Then find your chat id: open https://api.telegram.org/bot<token>/getUpdates in a browser and copy message.chat.id.
  3. n8n → New workflow → name it “Synapse → Telegram”.
  4. Add node Webhook: HTTP Method POST; Path synapse-telegram; Authentication Header Auth; Respond When Last Node Finishes (so Synapse sees failures).
  5. Click + after it → Telegram → Send a text message. Credential: paste the bot token. Chat ID: your chat id (or {{ $json.body.to }} to let Synapse choose). Text: {{ $json.body.message }}.
  6. Save → Activate. Copy the Webhook node's Production URL.
  7. .env: SYNAPSE_N8N_WEBHOOKS=telegram=<production URL> → restart Synapse.

Test it without Synapse first (use the secret you generated):

curl -X POST "<production URL>" -H "Content-Type: application/json" \
  -H "X-Synapse-Secret: <secret>" -d '{"to":"me","message":"hello from n8n"}'

Then in Synapse: “Send me a Telegram message with my open tasks”. It plans list_tasks → write → run_workflow, and asks for your signature before sending.

9.8  Recipe: inbound WhatsApp auto-reply

WhatsApp TriggerMessages
→
Ifis a text message
→
HTTP RequestPOST Synapse /api/messages
  1. Synapse must be reachable from n8n: same machine (http://localhost:8000; from n8n in Docker use http://host.docker.internal:8000), or a tunnel URL (section 10.4). Set SYNAPSE_API_TOKEN.
  2. n8n → new workflow → WhatsApp Trigger, Updates: messages, credential = the Meta app (client ID/secret from the app's Basic settings). n8n registers the callback with Meta when you activate.
  3. If node: condition {{ $json.messages[0].type }} is equal to text (ignores read receipts and media). Open the trigger's output panel once to confirm these field names — Meta sometimes nests them differently.
  4. HTTP Request (true branch): Method POST; URL <synapse>/api/messages; Authentication: Generic → Header Auth with name Authorization, value Bearer <SYNAPSE_API_TOKEN>; Send Body → JSON: 
    {
  "source": "whatsapp",
  "sender": "{{ $json.messages[0].from }}",
  "text":   "{{ $json.messages[0].text.body }}"
}
  5. Activate. The outbound whatsapp workflow from 9.5 must also be registered — Synapse replies through it.

What happens next: Synapse classifies the message. Routine (greeting, thanks, simple question, confirming a time): it drafts a short reply in your voice and sends it with run_workflow("whatsapp", {to: sender, message}). Anything involving money, commitments, sensitive topics or an upset tone: no reply — you get a notification with a suggested draft. The incoming text is treated strictly as data, never as instructions.

Replies wait for your one-click approval by default run_workflow is classed high-risk, so each reply appears under “◐ to sign” in the dashboard. To let routine replies go out on their own, change "run_workflow": "high" to "medium" in synapse/guardrails.py (medium still asks whenever the content came from the web). Do this only once you trust its judgement on a week of real messages.

Telegram works the same way: Telegram Trigger → HTTP Request with "source": "telegram", "sender": "{{ $json.message.chat.id }}", "text": "{{ $json.message.text }}", and a registered telegram workflow for replies.

10.1  Your Mac, always on

A launch agent starts Synapse at login and restarts it if it crashes. Replace <you> twice:

cat > ~/Library/LaunchAgents/com.synapse.api.plist <<'PLIST'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>com.synapse.api</string>
  <key>ProgramArguments</key>
  <array><string>/Users/<you>/Desktop/synapse/.venv/bin/synapse-api</string></array>
  <key>WorkingDirectory</key><string>/Users/<you>/Desktop/synapse</string>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>StandardOutPath</key><string>/tmp/synapse.log</string>
  <key>StandardErrorPath</key><string>/tmp/synapse.err</string>
</dict></plist>
PLIST

launchctl load ~/Library/LaunchAgents/com.synapse.api.plist
brew services start ollama
  • Logs: tail -f /tmp/synapse.err. Stop: launchctl unload ~/Library/LaunchAgents/com.synapse.api.plist.
  • After changing .env or pulling code: unload, then load again.
  • Scheduled goals run only while the Mac is awake: System Settings → Battery → Options → Prevent automatic sleeping when the display is off (on power adapter).

10.2  Docker

cp .env.example .env                       # fill it in (section 3)
VAULT_PATH="/Users/<you>/Documents/<YourVault>" docker compose up -d --build
docker compose logs -f
curl http://127.0.0.1:8000/api/health
  • docker-compose.yml reads your .env, then fixes the paths inside the container (/vault, /data) and points at Ollama on the host.
  • The vault is a bind mount: notes land on your disk and Obsidian sees them live. ./data holds all state.
  • The port is published on 127.0.0.1 only. Add the crew with SYNAPSE_EXTRAS=google,crew docker compose up -d --build.
  • Update: git pull && docker compose up -d --build. The healthcheck marks the container unhealthy if the API stops answering.

10.3  VPS with HTTPS

For a small Ubuntu VM (1 vCPU / 2 GB is enough; any provider). You need a domain or subdomain pointing at its IP (DNS A record, e.g. synapse.<yourdomain>).

# on the server, as a sudo user
sudo apt update && sudo apt install -y docker.io docker-compose-v2 git caddy
sudo usermod -aG docker $USER && newgrp docker
git clone https://github.com/<your-username>/synapse.git && cd synapse
cp .env.example .env && nano .env           # VPS values from 3.8; chmod 600 .env
mkdir -p vault && VAULT_PATH=./vault docker compose up -d --build

Caddy obtains and renews the TLS certificate automatically. /etc/caddy/Caddyfile:

synapse.<yourdomain> {
    reverse_proxy 127.0.0.1:8000
}
sudo systemctl reload caddy
sudo ufw allow OpenSSH && sudo ufw allow 80,443/tcp && sudo ufw enable
The vault on a server On a VPS the vault is a folder on the server, not the one Obsidian opens on your Mac. Sync it (Obsidian Sync, Syncthing, or a private git repo) if you want both. This is why 10.1 is the default.

10.4  Tunnels: reach your Mac from your phone or from n8n

Quick, temporary URL

brew install cloudflared
cloudflared tunnel --url http://localhost:8000     # prints https://<random>.trycloudflare.com

The URL changes each time — fine for testing, not for n8n.

Stable URL (free, needs a domain on Cloudflare)

cloudflared tunnel login
cloudflared tunnel create synapse
cloudflared tunnel route dns synapse synapse.<yourdomain>
cloudflared tunnel run --url http://localhost:8000 synapse
sudo cloudflared service install                    # keep it running across reboots

ngrok works too: ngrok http 8000 (a free static domain is available in its dashboard).

One token, one user Synapse is single-user: SYNAPSE_API_TOKEN is the whole authorisation model, with no accounts or roles. Anyone with the URL and the token can read your vault and send mail as you. Share neither.

11Pre-launch checklist

Tick every line before the port is reachable by anything but your Mac.

Correctness

  • uv run pytest -q passes
  • uv run python -m evals.run passes
  • uv run ruff check synapse evals tests clean
  • npm run build without warnings
  • uv run synapse doctor shows the right vault
  • CI green on GitHub

Operations

  • data/ and the vault are backed up
  • /api/health returns 200
  • You know how to roll back (12.3)
  • You know where the logs are

Security

  • SYNAPSE_API_TOKEN is a long random value
  • SYNAPSE_HOST=127.0.0.1; access only via tunnel or Caddy
  • HTTPS on every public URL
  • .env, data/ never committed; chmod 600 .env on servers
  • Approvals left on for email, deletes and workflows
  • SYNAPSE_N8N_WEBHOOKS lists only workflows you built
  • SYNAPSE_N8N_SECRET set and checked in n8n

First hour after going live

  1. curl https://<your-url>/api/health from your phone's network returns 200.
  2. curl https://<your-url>/api/runs without the token returns 401.
  3. Run one real goal and approve one risky action end to end.
  4. Check the trace (Show working) recorded it and the Evals tab still loads.
